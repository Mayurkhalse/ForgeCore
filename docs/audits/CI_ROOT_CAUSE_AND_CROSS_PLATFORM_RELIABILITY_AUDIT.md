### Root Cause 1: `test_workflow_golden.py` Assertion Over-Constraint
In commit `6ea8bc0`, `tests/e2e/test_workflow_golden.py` asserted:
```python
assert len(verify_report["findings"]) == 0
```
However, the synthetic test project fixture generated by `tests/e2e/fixtures.py` contained code that triggered Ruff linter warnings:
- `line-length = 100` in fixture `pyproject.toml` clashed with lines exceeding 100 characters in the generated app.
- Type annotations in `fixtures.py` used `Optional[str]` without `from __future__ import annotations`, triggering modern typing linter rules.
When ForgeCore's `verify_project` executed `ruff` during Stage H verification, it reported 2 non-blocking lint findings. The golden test asserted zero total findings, causing an immediate `AssertionError`.

### Root Cause 2: Starlette `TestClient` Socket Deadlocks & 10-Minute Timeout
In commit `6ea8bc0`, `fixtures.py` declared:
```python
FASTAPI_TESTCLIENT_SHIM = '''"""Lightweight test client shim over Starlette."""
from starlette.testclient import TestClient
'''
```
Starlette's `TestClient` uses AnyIO's `BlockingPortal` (`anyio.from_thread.start_blocking_portal()`), which starts a daemon worker thread running `asyncio.run()`.
- On Windows and macOS runners, initializing the asyncio event loop invokes `_make_self_pipe()`, which calls `socket.socketpair()`.
- On Windows, `socket.socketpair()` creates a local loopback TCP connection to `127.0.0.1`. In restricted runner network environments or sandboxes, loopback connection drops/hangs cause `lsock.accept()` to block indefinitely.
- On macOS, cross-thread event loop dispatching inside sub-processes spawned by `pytest` caused worker threads to block waiting for portal synchronization.
- With `pytest-timeout` configured to 60.0s per test, sequential hanging tests accumulated over 600 seconds (10 minutes) until the job timed out.

### Root Cause 3: Matrix Python Version Discrepancy
The CI workflow defined:
```yaml
matrix:
  os: [ubuntu-latest, windows-latest, macos-latest]
  python-version: ["3.11", "3.12", "3.13"]
```
While `pyproject.toml` had:
```toml
requires-python = ">=3.13"
```
When Python 3.11 and 3.12 jobs ran `uv sync`, `uv` detected that the active runner Python did not satisfy `>=3.13`. While `uv` attempted to download Python 3.13.17 on `macos-latest`, on other runners `uv sync` failed or required downloading secondary Python binaries, leading to matrix failures.

### Upgraded ASGI Dispatcher Architecture
The test client in `tests/e2e/fixtures.py` was upgraded to construct standard ASGI 3.0 HTTP scopes:
```python
scope = {
    "type": "http",
    "asgi": {"version": "3.0", "spec_version": "2.4"},
    "http_version": "1.1",
    "method": method.upper(),
    "path": path,
    "raw_path": path.encode("ascii"),
    "query_string": query.encode("ascii"),
    "headers": req_headers,
    "client": ("127.0.0.1", 50000),
    "server": ("testserver", 80),
}
```
The ASGI coroutine `self.app(scope, receive, send)` is driven synchronously in-process:
- Zero threads spawned.
- Zero network sockets opened.
- Zero reliance on loopback networking (`127.0.0.1`).
- Preserves genuine ASGI application routing, exception mapping, and response serialization.

```python
fail_on = config.verify.fail_on
```

2. **Observability of Non-Blocking Findings:**
   - Medium and low findings are **never suppressed**. They remain fully populated in `verify_report["findings"]` and categorized in `verify_report["summary"]`.
3. **Negative Test Verification (`test_golden_e2e_blocks_on_high_severity_finding`):**
   - Added a negative test that injects a failing test into the simulated patch.
   - Verified that `verify_report["status"] == "failed"`.
   - Verified `len(blocking_findings) >= 1`.
   - Verified `verify_report["next_action"]` directs the agent to fix blocking findings and does NOT emit `"Ready for review"`.
